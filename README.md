# Pi Herdr Mesh

Local communication and discovery between Pi processes owned by the same OS user.

Install as a Pi package from GitHub:

```sh
pi install git:github.com/dardT/pi-herdr-mesh
```

Run `/reload` in existing Pi sessions after installing or updating. If updating from `pi-mesh`, remove the old package or standalone copy first to avoid loading both extensions. Reload each session to get the new commands and tools; mesh membership ends on reload, so run `/mesh` again. The legacy `/mesh:listen` command is no longer registered. The manifest declares `@dardt/pi-herdr-mesh` for a future npm release; it is **not published to npm yet**.

## Commands

| Command | Meaning |
| --- | --- |
| `/mesh` or `/mesh on` | Join the mesh: become visible in the catalog, accept requests, and enable outgoing sends. Starts off by default; ID is derived from the saved Pi session. |
| `/mesh off` | Leave the mesh: stop receiving, leave the live catalog, disable new outgoing sends, and best-effort cancel queued outgoing BTW. Started work cannot be undone. |
| `/mesh status` | Show whether this session belongs to the mesh and its ID. |
| `/mesh:steer [--delayed] <id> <prompt>` | Start a normal turn in the target. Both request and answer **remain in its conversation**. Rejects a busy target. |
| `/mesh:btw [--delayed] <id> <question>` | Queue a tool-free, one-off model answer based on the target's finalized context. **Neither the question nor answer enters its conversation.** |
| `/mesh:wait <id> <request-id>` | Wait up to 30 seconds for a delayed steer or BTW reply; repeat if pending. |
| `/mesh:requests [request-id]` | List locally tracked delayed requests. In the TUI, select one to wait, view its reply, or cancel/dismiss; pass a request ID to display its current saved result. |
| `/mesh:cancel <request-id>` | Cancel a queued BTW at the listener when possible; otherwise dismiss it from local tracking without undoing target work. |
| `/mesh:catalog` | Display **all** registered sessions under this OS user, across Herdr workspaces, with this session marked `← you`. |
| `/mesh:catalog ws` | Display only sessions in the current Herdr workspace (on this Herdr server). The quoted spelling `"ws"` also works. |
| `/mesh:catalog:refresh` | Sync the catalog; refresh changed purposes across all listening sessions. |
| `/mesh:catalog:refresh ws` | Sync the catalog; refresh changed purposes only for listening sessions in the current Herdr workspace (on this Herdr server). The quoted spelling `"ws"` also works. Requires a Herdr-managed pane. |
| `/mesh:catalog:refresh <id>` | Sync the catalog; refresh the changed purpose for just that session. |

Target IDs are offered as argument completions for `/mesh:steer`, `/mesh:btw`, `/mesh:wait`, and `/mesh:catalog:refresh <id>`; only listening recipients appear for steer/BTW. The catalog shows each session's live idle/busy/answering-BTW activity and queued BTW count (updated as events occur). Busy steer targets still reject requests; queued BTW requests still wait for idle. Catalog listing prunes exited processes without requiring a purpose refresh.

In the interactive TUI, catalog refresh shows a footer progress bar while it discovers sessions and queries changed purposes. The counter tracks attempted purpose queries (including failures), not every catalog row; the bar clears on completion or error. A refresh with nothing to query can finish too quickly to notice the bar.

Only processes that run `/mesh` or `/mesh on` join the live catalog and accept incoming requests or purpose queries. A member must also be on to send, wait, cancel, or refresh purposes; catalog listing remains available while off. The catalog is shared across same-user processes, but is not a system-wide process scanner: already-running Pi processes must `/reload` (or restart) to load Pi Herdr Mesh, then join before they appear. Sessions under another OS account are intentionally excluded. The sender's mesh ID identifies it in the extension-generated header delivered to the target. The header also includes the target ID, request ID, and whether the request is `steer` or `btw`. Sender-provided text is explicitly delimited and does not change the target's standing purpose merely by being sent.

Agent tools: `mesh_steer({ id, text, delayed? })`, `mesh_btw({ id, text, delayed? })`, `mesh_wait({ id, requestId })`, `mesh_requests({ requestId? })`, `mesh_cancel({ requestId })`, and read-only `mesh_catalog({})`. Tool results enter the **sender's** calling agent context. Slash-command replies display without starting a new sender turn. `--delayed` returns a request ID immediately; blocking requests have no processing deadline and stop when the listener disconnects. `/mesh:btw` queues until the target is idle, then processes one request at a time; its answer may incur a full-context model call, but it does not run tools or persist messages in the target.

Catalog purposes are generated by these same context-only queries, not inferred on startup. Catalog refresh does not query non-listening sessions, and does not re-query unchanged conversations. Purpose generation costs a model call per changed listening session; a model failure leaves the prior purpose available for retry. BTW and purpose calls are billed as direct model requests, but their usage is not recorded in the target's Pi session transcript. Prompt-cache hits depend on the provider and the unchanged prompt prefix and are not guaranteed. If the target's model has no credentials, BTW and purpose refresh can fail. A catalog row may retain stale purpose until refreshed.

Mesh IDs are stable, short hashes of Pi's saved session ID: reloading or resuming the same saved session gets the same ID; a new Pi session gets a new ID. Two running copies of one saved session cannot both join—the second is rejected. The live catalog does not retain offline rows. `ws` is reserved for workspace refresh. IDs must be unique among running Pi Herdr Mesh instances. Request IDs are separate UUIDs, available until the listener stops or evicts old completed results (up to 100 retained). The sender tracks delayed requests only in memory; no prompt text is retained by its request list. Up to 100 completed entries are retained locally, while pending entries remain until dismissed. Status is the last **checked** state, not a background subscription: use `/mesh:wait` or select Wait in `/mesh:requests` to update it. Cancelling removes queued BTW at the target and wakes its waiters; an already-running BTW or steer continues, and only local tracking is dismissed. A listener that disconnects cannot confirm cancellation. Sender tracking clears on `/mesh off`, reload/session replacement, or exit. On graceful quit and Pi's SIGTERM/SIGHUP shutdown, the `session_shutdown` hook removes membership and closes the socket. SIGKILL/crashes cannot run hooks; catalog reads prune dead PIDs, and stale sockets are handled when rejoining. Membership ends on session replacement, reload, or exit; the new session must opt in again.

## Local transport and caveats

The extension uses Unix-domain sockets and catalog files in a private (0700) temporary directory under the current OS user, with socket and file permissions 0600. The transport directory retains its previous `pi-mesh-<uid>` name for compatibility with running listeners and to keep Unix-socket paths short on macOS. It opens no TCP ports. It cannot protect against malicious code running under the same OS account. Requests and replies are capped at 1 MiB. An outgoing request may appear in the sender's own history (especially if sent by an agent tool); **BTW isolation applies to the target only**. Concurrent edits to the target's project by other processes are outside this guarantee.

Blocking calls can deadlock in cyclic workflows (for example, A waits for B while B waits for A). Use `--delayed` and `/mesh:wait` when coordinating cycles. A queued BTW request waits for the target to settle; there is no automatic deadline for the entire request.
